Gameplay Framework Map

Where your game logic actually lives. Every class family in the engine, what each one owns, and the rule that decides which one your next feature belongs in. Two hierarchies matter: inheritance tells you what a class is; ownership tells you who spawns it and who can see it.

Two ways in. Know the class name? Type it in the filter above and everything else disappears. Know the feature but not the class? Go straight to Which class owns it.

Decision rules

Eight checks that resolve most placement questions

01

Controller is the will, Pawn is the body. Input handling and decisions go in the Controller; movement, collision and presentation go in the Pawn. Bind input inside your Character and you will regret it the first time you write a bot.

02

If a client needs to know it, it cannot live in the GameMode. Move it to GameState (everyone) or PlayerState (one player). The GameMode decides; the states publish.

03

If it must survive the Pawn dying, it belongs in PlayerState. Score, team, loadout, unlocks. Anything on the Pawn is gone the moment it is destroyed.

04

If it must survive a level change, it belongs in GameInstance. Or a UGameInstanceSubsystem — same lifetime, less boilerplate, no manual singleton.

05

If two unrelated actors need the same behavior, it is a component. Not a new base class. A door, a crate and an enemy can all carry a health component; they should not share an ancestor.

06

Anything that decides an outcome runs on the server. Guard it with HasAuthority(). The client asks with a Server RPC and waits to be told; it never applies the result itself.

07

If a designer will ever want to change the number, it is data. A UDataAsset or a UDataTable, not a constant in a header they cannot recompile.

08

If it does not need to run every frame, it should not tick. Default bCanEverTick to false and use timers, delegates and events. This is the single cheapest performance decision in the engine.

Failure modes

The bugs this hierarchy causes, and why

SymptomCause and fix
GetWorld() returns nullYou are in a constructor. The CDO is built at editor startup with no world. Move the work to BeginPlay or PostInitializeComponents.
Values set in the constructor appear on every instanceThe constructor builds the Class Default Object. It is for defaults, never for gameplay.
GetPlayerState() is null in BeginPlay on a clientReplication order is not guaranteed. React in OnRep_PlayerState or PossessedBy instead.
GetAuthGameMode() is nullYou are on a client. The GameMode never exists there. Read GameState instead.
A Server RPC silently does nothingThe calling client does not own that actor. Set Owner at spawn, or route the call through the PlayerController.
A replicated property never arrivesMissing bReplicates = true, missing GetLifetimeReplicatedProps, or on a component, missing SetIsReplicatedByDefault(true).
Overlap events never fireSetGenerateOverlapEvents(true) is required on both components, and their channel responses must be Overlap on both sides.
A pointer becomes garbage mid-frameA UObject* member without UPROPERTY() is invisible to the garbage collector. Mark it, or use TWeakObjectPtr.
Cooked build is enormousHard references. One Blueprint casting to another pulls it and everything it references into memory. Use interfaces and TSoftObjectPtr.
Animation causes a crash or a raceGameplay writes from NativeThreadSafeUpdateAnimation, which runs off the game thread. Read only there.
Frame rate dies with actor countEverything ticks. Set PrimaryActorTick.bCanEverTick = false as the default and opt in deliberately.
A delegate fires on a destroyed objectYou never unbound it. Unbind in EndPlay, and keep the FDelegateHandle when you bind a lambda.
UI text cannot be translatedYou used FString. Player-facing text is FText, always.
Works in PIE, breaks in a packaged clientPIE runs server and client in one process, so authority bugs stay hidden. Test with Play As Client and two players.
Execution order

Lifecycle — when each function actually runs

Half of all "it works in the editor but not in a build" bugs are an assumption about this order. GetWorld() is null in a constructor; PlayerState is null in a client's BeginPlay.

Actor spawned at runtime
  1. UWorld::SpawnActor
  2. PostSpawnInitialize
  3. PostActorCreated — the constructor has run
  4. ExecuteConstruction → OnConstruction
  5. PostActorConstruction
  6. PreInitializeComponents
  7. UActorComponent::InitializeComponent
  8. PostInitializeComponents — components exist and are safe
  9. UWorld::OnActorSpawned broadcast
  10. BeginPlay — the world exists; start here
Actor placed in a level
  1. PostLoad — loaded from disk, mutually exclusive with PostActorCreated
  2. UAISystemBase::InitializeActorsForPlay
  3. ULevel::RouteActorInitialize
  4. PreInitializeComponents
  5. UActorComponent::InitializeComponent
  6. PostInitializeComponents
  7. BeginPlay
Teardown
  1. EndPlay(Reason) — unbind everything here
  2. Destroyed
  3. Garbage collection, eventually
GameMode startup, in order
  1. InitGame — before any actor's BeginPlay
  2. InitGameState
  3. PreLogin — approve or reject the connection
  4. Login — spawns the APlayerController
  5. PostLogin — controller exists, safe to touch
  6. HandleStartingNewPlayer
  7. RestartPlayer → ChoosePlayerStart → spawns the Pawn
  8. APawn::PossessedBy then APlayerController::AcknowledgePossession
Tick groups, in frame order
  1. TG_PrePhysics — default; gameplay reads last frame's physics
  2. TG_StartPhysics → TG_DuringPhysics
  3. TG_EndPhysics → TG_PostPhysics — physics results are final
  4. TG_PostUpdateWork — cameras and anything that must see everything
Component lifecycle
  1. OnRegister → InitializeComponent → BeginPlay
  2. TickComponent
  3. EndPlay → OnUnregister → OnComponentDestroyed

Ownership

The framework eight — who spawns whom

Indentation here means "is created and owned by", not "inherits from". This is the tree that decides your architecture: a class can only reach what sits above or beside it.

Inheritance

Inheritance

Components — where most of your code should end up

Three tiers, and the difference matters: UActorComponent has no transform, USceneComponent adds one and can be attached, UPrimitiveComponent adds geometry so it renders and collides. Pick the shallowest tier that does the job.

  • UUActorComponentReusable behavior bolted onto an Actor. No transform. Ticks, replicates, and can be added by Blueprint or at runtime.
    • UUSceneComponentAdds a transform. Can attach to a parent and to sockets; forms the actor's component tree.
      • UUPrimitiveComponentAdds geometry, so it renders and collides. All collision, overlap and hit events originate here. Owns an FBodyInstance.
        • UUMeshComponentAnything with materials.
          • UUStaticMeshComponentRigid geometry.
            • UUInstancedStaticMeshComponentMany copies, one draw call. UHierarchicalInstancedStaticMeshComponent adds LOD and culling per instance — what foliage uses.
            • UUSplineMeshComponentA mesh deformed along a spline — roads, cables, pipes.
          • UUSkinnedMeshComponentSkinned geometry.
            • UUSkeletalMeshComponentSkinned mesh + an UAnimInstance + optional physics asset for ragdoll. The single busiest component in most games.
          • UUProceduralMeshComponentRuntime-built geometry. UDynamicMeshComponent is the newer GeometryScript-friendly one.
        • UUShapeComponentInvisible collision primitives — the cheapest colliders available.
          • UUCapsuleComponentThe Character's root collider. Siblings: UBoxComponent, USphereComponent.
        • UUSplineComponentA path in space. Query points, tangents and distances along it.
        • UUWidgetComponentA UMG widget rendered in the 3D world — nameplates, world-space UI.
        • UUNiagaraComponentA running VFX system instance.
        • UUArrowComponentEditor-only gizmo. Sibling: UBillboardComponent.
      • UUCameraComponentA view point. UCineCameraComponent adds lens, focus, aperture.
      • UUSpringArmComponentA collision-aware camera boom with lag. The third-person camera in one component.
      • UUAudioComponentA positioned, controllable sound instance — pause, fade, set parameters.
      • UULightComponentBase→ ULightComponent → UDirectionalLightComponent, UPointLightComponent → USpotLightComponent, URectLightComponent; USkyLightComponent.
      • UUDecalComponentProjects a material onto surfaces — bullet holes, blood, tyre marks.
      • UUPostProcessComponentPost-process settings attached to an actor rather than a volume.
      • UUSceneCaptureComponent2DRenders the scene into a UTextureRenderTarget2D — mirrors, security cameras, portals, data bakes.
      • UUChildActorComponentSpawns and owns a whole Actor as a component. Convenient, and a common source of surprise costs.
      • UUPhysicsConstraintComponentA joint between two physics bodies — hinges, ropes, ragdoll limits.
    • UUMovementComponentMoves an UpdatedComponent; renders nothing itself.
      • UUNavMovementComponent→ UPawnMovementComponent, the base for anything a Controller drives.
        • UUCharacterMovementComponentMovement modes, root motion, crouching, and full client-side prediction with server correction. The largest class most projects ever touch.
        • UUFloatingPawnMovementSimple fly/hover movement with no gravity.
      • UUProjectileMovementComponentBallistic, homing and bouncing motion.
      • UURotatingMovementComponentConstant spin with no physics cost.
    • UUInputComponentBinds input to functions. UEnhancedInputComponent is the current one.
    • UUBrainComponent→ UBehaviorTreeComponent, the AI's running logic.
    • UUBlackboardComponentThe AI's key/value working memory.
    • UUAIPerceptionComponentSight, hearing and damage senses; reports stimuli to the controller.
    • UUPathFollowingComponentWalks a computed path. UCrowdFollowingComponent adds avoidance.
    • UUAbilitySystemComponentThe GAS bridge — abilities, effects, attributes, tags.plugin
    • UUTimelineComponentThe C++ side of a Blueprint Timeline — curve-driven values over time.
    • UUPhysicsHandleComponentGrab and drag a physics body — the gravity-gun component.
    • UURadialForceComponentExplosion impulses and radial damage falloff.
    • UUPCGComponentRuns a PCG graph using this actor's bounds as input.plugin
    • UUStateTreeComponentRuns a StateTree on this actor — the newer alternative to a behavior tree.plugin
The object model

Core objects — what makes a class visible to the engine

Everything the engine can save, garbage-collect, replicate or show to Blueprint descends from UObject. These classes are the reflection machinery; you rarely subclass them, but every bug about "my pointer became null" or "Blueprint can't see this" lives here.

  • UUObjectRoot of the reflected type system: garbage collection, serialization, replication, Blueprint exposure, GetWorld(), and the CDO (Class Default Object) that holds your constructor's values.
    • UUStructAnything that owns a property list.
      • UUClassRuntime type info for a UObject class. What StaticClass(), GetClass() and SpawnActor<T> actually pass around.
      • UUScriptStructReflection for a USTRUCT() — lets a plain struct appear in Blueprint and replicate.
      • UUFunctionReflection for a UFUNCTION(). How Blueprint calls C++, and how RPCs are routed over the wire.
    • FFPropertyReflection for a UPROPERTY(). Was UProperty before 4.25 — old tutorials still say the wrong name.
    • UUPackageOne .uasset file loaded into memory. The unit of save, load and cook.
    • UUBlueprintThe editor-only asset. At runtime you never touch it — you get its compiled UBlueprintGeneratedClass.
    • UUInterfaceDeclared as a U…/I… pair. A behavior contract shared by classes with no common ancestor.
    • UUEngineProcess root. UGameEngine in a packaged build, UEditorEngine in the editor. Reachable as GEngine.
    • UUGameViewportClientThe window the game renders into. Routes raw input to the right ULocalPlayer, owns split-screen layout.
    • UUDeveloperSettingsSubclass it and your properties appear in Project Settings automatically, backed by a config .ini.

Outside the UObject tree

Plain types — structs, containers and pointers

None of these are garbage-collected. Pointer choice is where most memory bugs are born, so the table below is worth memorising.

Pointers — pick the right one

TypeUse it when
TObjectPtr<T>A hard reference held in a UPROPERTY(). Keeps the object alive. The modern form of a raw UObject* member.
TWeakObjectPtr<T>You want to observe without keeping alive. Always IsValid() before use. Correct for caches and back-pointers.
TSoftObjectPtr<T>You want the path now and the asset later. Nothing loads until you ask.
TSubclassOf<T>You need a class, not an instance, and want the editor to offer only valid ones.
TSharedPtr<T> / TUniquePtr<T>Non-UObject C++ objects only. Never for UObjects — the GC does not know about them.
raw UObject* with no UPROPERTYNever. The garbage collector will delete it while you still hold the pointer.

Strings — three types, not interchangeable

TypeUse it for
FNameIdentifiers: bone names, socket names, data table row keys, tags. Interned, case-insensitive, comparison is an integer compare.
FStringMutable working text: building a path, parsing, logging. Heap-allocated, so avoid in hot loops.
FTextAnything a player reads. Carries localisation and number/date formatting. Never build one with string concatenation.

Everything else

TypeResponsibility
FVector, FRotator, FQuat, FTransformPosition, Euler rotation, quaternion rotation, and the combined location/rotation/scale. Interpolate with FQuat, author with FRotator.
FBox, FSphere, FPlane, FMatrixBounds and linear algebra.
FLinearColor / FColorFloat colour for maths and materials; packed 8-bit colour for storage.
TArray<T>, TMap<K,V>, TSet<T>The containers. TArray is contiguous — Reserve() before a known-size fill.
TOptional<T>, TVariant<...>, TTuple<...>Maybe-a-value, one-of-several, and fixed heterogeneous pairs.
FHitResult, FOverlapResultWhat a query returned.
FGameplayTagA hierarchical identifier registered project-wide. Cheap to compare, matches by parent.
FTimerHandle, FDelegateHandleHandles you must keep in order to cancel or unbind later.
FGuid, FDateTime, FTimespanUnique ids and time.

Enhanced Input

Input — assets, not hardcoded key names

The old UPlayerInput axis/action mappings still work but are legacy. Enhanced Input replaces them with assets you can swap at runtime, which is what makes context-sensitive controls and rebinding tractable.

ClassResponsibility
UInputActionAn asset naming one thing the player can do — "Move", "Jump", "Fire" — with a value type: bool, 1D axis, 2D axis or 3D.
UInputMappingContextAn asset mapping keys to actions, with modifiers and triggers per key. Swap contexts to change what the controls mean (on foot / in vehicle / in menu).
UEnhancedInputComponentBinds an action + trigger event to one of your functions. Lives on the Pawn or the PlayerController.
UEnhancedInputLocalPlayerSubsystemWhere you add and remove mapping contexts at runtime, with priorities.
UInputModifierPre-processes the raw value: dead zone, negate, swizzle axes, scale, smooth.
UInputTriggerDecides when the action fires: Down, Pressed, Released, Hold, Tap, Chorded.
FInputActionValueThe value delivered to your handler. Get<bool>(), Get<float>(), Get<FVector2D>().
ETriggerEventStarted / Triggered / Ongoing / Completed / Canceled — pick deliberately, they are not interchangeable.
UEnhancedInputUserSettingsPlayer-facing key rebinding, saved per user.

One caveat about the future

Everything above is the current 5.x framework and is what you should build on today. Epic has signalled that in Unreal Engine 6 a Verse-based Scene Graph will eventually sit where the Actor system sits, with Blueprints and Actors deprecated once it matures — but Actors and Blueprints stay fully supported through UE6 Early Access, and conversion tooling is promised. Reported dates are Early Access around late 2027 and a final release around 2029.

That paragraph comes from press coverage of Epic's announcements, not from the engine documentation. Treat the dates as soft.
